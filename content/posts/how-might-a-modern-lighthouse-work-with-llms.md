Lighthouse is one of the most successful developer tools the web has ever shipped, and the thing that has always nagged at me about it is that every audit in it is a hand-written piece of JavaScript. Someone had to sit down, understand a best practice, encode it as a deterministic check, ship it, and maintain it as the platform moved underneath it. That is a lot of work for one audit. Multiply it by a hundred and you start to see why the catalog grows slowly and why whole categories of "is this any good" are quietly out of reach. The checks can only ever test what someone bothered to write a test for.

A few months ago I got obsessed with a simple question: what if the audit was just a sentence? What if you could describe, in plain English, what good looks like, and let a model figure out how to check it? I wrote that down as an idea I called "tests as prompts" at the time, after a chat with Michael Hablich about where Lighthouse and skills might meet. It sat as a seed for a while. Then I had the pieces to actually build it, and I built a thing called web-uplift. This post is about what it is, why it is shaped the way it is, and why I think the model behind it is more interesting than the tool.

Let me start with what it does, because the shape only makes sense once you see the loop.

You point web-uplift at a URL. It explores the site, works out which pages and flows actually matter (a homepage, an article template, a form, a listing, not just the one page every audit happens to hit), and then it judges the site against a set of principles. Then, if you give it the source code, it fixes what it found and runs the whole thing again. Find, fix, test. Find, fix, test. It keeps going until there is nothing left to fix.

That loop is the part I want you to hold onto. But to understand why it works, you have to understand the three things it is built from, because the interesting bet is in how they are wired together.

The first ingredient is a spec of what good looks like. I did not invent this. Una Kravets gave a talk at Google I/O 2026 called "What's new in Web UI" where she laid out five principles for modern UX: respect user preferences, implement natural interactions, provide guided navigation, maximize content and reduce noise, and adapt to the form factor. I took those five and expanded them out, folding in the dimensions Lighthouse already measures (performance and Core Web Vitals, accessibility, best practices, discoverability) plus a handful the modern web forces you to care about now (privacy and security, resilience, internationalisation, being trustworthy rather than manipulative, sustainability, and whether your site is ready for agents to read it). Seventeen principles in the end. Each one is written as an outcome, not a check. "The surface follows the user's colour scheme preference." "Animations respect reduced motion." "The primary task succeeds." Each has a hint about how you might detect it and a pointer into the guidance for how to fix it, but the hint mandates nothing.

The second ingredient is the guidance itself, the how. This is Modern Web Guidance, a machine-readable feed of about 137 use-case-based best practices that you can search and pull from over npm. When the model finds a problem, it does not have to guess at the fix, it looks up the recommended modern approach. This matters more than it sounds. It is the difference between an audit that says "this is bad" and one that says "this is bad, and here is exactly how to do it right, grounded in the current platform."

The third ingredient is the one I argued with myself about the most, and it is the actual bet of the whole project. There are no hard-coded checks in web-uplift. None. The runtime is a generic set of evidence primitives over raw Chrome DevTools Protocol: take a screenshot, capture a video of a transition, grab a heap snapshot, read the layout metrics and CLS, pull the DOM and the local source, run arbitrary JavaScript in the page, run Lighthouse, inject axe-core. That is it. The primitives give the model senses. They return data and artifacts. They never decide anything. Every single judgement, whether a principle passes or fails, is made by the model reasoning over that evidence.

This is where it gets exciting for me. Because the tests are plain text and the judge is a model, authoring a new audit is no longer a programming task. It is a writing task. You describe the outcome you want. The model works out which of its senses it needs (a screenshot, a video under reduced motion, a heap snapshot, a Lighthouse run) and goes and gets the evidence and makes the call. You do not have to teach it how to check if a page honours dark mode. You tell it the page should honour dark mode. It emulates the preference, reads the computed colours, and tells you what it found, with a screenshot attached as proof.

And the senses are extraordinary now. We can show the model a video of an animation and ask whether it respects reduced motion. We can hand it a heap snapshot and ask whether memory is climbing on a long session, which is exactly what my other project, memory-tracer, does for leak hunting. We can let it run commands, read traces, read a HAR of the network, read the actual authored source next to the rendered DOM. We are at a moment where plugging all these capabilities together is suddenly cheap, and the thing that used to be the hard part, encoding the test, has evaporated. Writing the test is just writing.

So does it actually work on something real? I ran it against my own sites, because they were conveniently broken and conveniently mine.

aifoc.us, this blog, was the first. It came back with six issues and three not-applicables. The render-blocking main.js and Font Awesome were dragging LCP out to around twelve seconds in the lab and a performance score of 57. Its own Content Security Policy was blocking its own Cloudflare Insights beacon. There was an empty meta description, multiple h1s, an untitled YouTube iframe, and a forced-dark that ignored anyone who actually wanted light mode. It also correctly noted the strengths (zero CLS, every image had alt text, accessibility 94). I let it fix them, re-audited, and the scores climbed. The point is not the scores. The point is that it found real things, on a real site, by looking.

paul.kinlan.me was the more satisfying one. The headline issue was that I was running the Tailwind Play CDN in production, which is a render-blocking, not-for-prod runtime that was pushing LCP to nearly ten seconds. The fix was a build-time purged Tailwind build, and because I could compare the before and after screenshots, I verified it was byte-identical CSS and visually identical, so I shipped it rather than PR'd it. It also caught a missing h1, duplicate landmarks, an empty meta description, vague link text, a forced-light that ignored dark mode, and missing security headers. Accessibility was already 100, best practices 100, zero CLS, and it even noticed I had view transitions, speculation rules, and RSS wired up. Again, it found the genuine problems and credited the genuine wins, in the same pass.

The thing I keep coming back to is that none of this is a single skill. The web-uplift skill is the methodology, but the actual capability is the composition: a plain-text spec of outcomes, a machine-readable feed of how to achieve them, a generic set of senses over a real browser, and a model in the middle that reads, judges, and writes fixes. Each of those pieces is reusable on its own. The "tests as prompts" framing from that original idea is the real product. web-uplift is just one instance of it, aimed at web quality. You could aim the same shape at anything you can describe as an outcome.

Now the part I think is genuinely new, and the reason I keep calling it a loop rather than a tool.

I originally framed this to myself as a question about auto-research. Could we do something like the autonomous research loops people run for other domains, but pointed at improving a website? It is not literally auto-research. But it shares the shape that matters: you set a goal, you use a model as the judge of whether you have met it, and you run a loop that keeps trying until the judge is satisfied. In web-uplift the goal is the seventeen principles. The judge is the model reading the evidence. The loop is audit, fix, re-audit. Find, fix, test. Find, fix, test. And it is a genuinely tight loop now, because the fix and the test are the same kind of intelligence. The thing that decides you have a contrast problem is the same kind of reasoning that writes the CSS to fix it, which is the same kind of reasoning that confirms the fix worked.

That tightness is what makes me think modern web development is about to change shape. For twenty years the cycle has been: build, then later, maybe, run a separate audit tool that tells you what you got wrong, then go back and fix it by hand. The audit and the fix lived in different worlds, run by different people on different schedules. When the auditor and the fixer are the same model, reading the same source, against a spec written in plain text, the cycle collapses. You describe the outcome. The model hunts toward it. You watch it climb the hill.

I do not think this replaces Lighthouse. Lighthouse's deterministic scores are valuable precisely because they are deterministic, and a CI pipeline wants a number it can trust run to run. What I think happens is that a second, parallel system grows up alongside it, one where the tests are authored as language and the judgements are made by reading, and that system can cover everything Lighthouse cannot afford to hand-code. The subjective stuff. The stuff that changes every Chrome release. The stuff nobody has written a check for yet.

The question I started with was how a modern Lighthouse might work with large language models. Having built a version of it, I think the answer is: you stop writing the audits, and you start writing the bar. The model does the rest, and it will keep doing the rest, in a loop, until your site clears it. That feels like a different kind of tool, and I suspect, a different kind of craft.
